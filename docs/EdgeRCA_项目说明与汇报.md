# EdgeRCA：小模型如何分工完成故障根因分析

更新：2026-10-19。第3节还原已运行版本的一道真实题；第5节说明本次接入的详细回复与多候选新版，尚无新版真实模型成绩。

## 1. 要解决什么问题，用什么方法

故障会产生大量指标、日志和调用记录。小模型一次读完很困难；提前压成固定摘要，又可能漏掉关键线索。

**我们让4B小模型分别整理各组件的信息，再让9B协调者综合判断；原始记录保留，缺少的信息可以补查。**程序计算数值，小模型解释现象，协调者比较不同组件，回答题目要求的故障时间、组件或原因。

```text
题目＋原始数据
    ↓ 按组件编号分开，按时间回放
原始记录入库＋程序检测变化
    ↓ 工具计算、整理
各节点的观测目录
    ↓ 4B选择展开、填写解释
18份节点报告＋业务变化＋实际调用关系
    ↓ 9B比较证据；必要时要求节点补查
最终答案 → 保存后再与标准答案比较
```

## 2. 18个节点是什么，数据怎样投放

**组件是系统里可以单独识别的运行对象，例如一个数据库、缓存或应用实例，不一定是一台物理设备。**Bank原始记录用 `cmdb_id` 标明所属对象。程序把相同编号的指标、日志和调用记录归到同一个节点。

18个编号是：IG01/02、MG01/02、Mysql01/02、Redis01/02、Tomcat01～04、apache01/02，以及dockerA1/A2/B1/B2。这个数量来自数据中的对象编号。数据没有完整的物理部署关系，所以当前模拟的是**18个组件节点**；它们复用同一个4B模型，各自保存记录。业务成功率等数据按业务编号单独保存，供协调者查看。

每10秒投递一批属于该时间段的记录。**各节点共用时间轴，但不保证每批都有新数据，也不保证都有三种数据。**下面是后文例题18:00—18:30窗口的实际原始记录条数：

| 节点 | 指标 | 日志 | 调用记录 |
|---|---:|---:|---:|
| Redis02 | 2,158 | 0 | 0 |
| Tomcat04 | 1,556 | 4,269 | 32,940 |
| dockerA2 | 11 | 0 | 25,366 |

这些是记录条数，不是故障数。某批没有新记录就不新增；某类数据缺失也不能填成“设备正常”。同一窗口的前3个10秒批次，分别只有18、14、14个节点收到新数据。

**当前实验先回放完整半小时，再调用4B和9B集中分析。**回放期间，程序已经保存原文、检测告警并记录变化。半小时是数据里的时间跨度，可以加速回放。10秒是投递间隔，不是模型必须完成分析的期限。当前尚未实现18台真实边缘设备同时接收数据、持续调用模型的运行方式。

## 3. 跟着一道真实题目，看每一步怎样变化

这里使用最新批量实验中的Bank第2题，即程序行号1。**下面展示实际运行，包括答错的环节，不是理想流程示意。**

### ① 输入：题目＋原始记录

题目大意：**2021年3月4日18:00—18:30发生一个故障，请找出根因组件和原因。**这道题不要求回答故障时间。标准答案此时不交给任何模型。

原始文件里是许多分散记录。下面摘取几条，时间已转换为便于阅读的北京时间，字段名作中文展示：

| 所属组件 | 时间 | 数据类型 | 原始记录表达的内容 |
|---|---|---|---|
| Redis02 | 18:00:00 | 指标 | 内存占比23% |
| Redis02 | 18:10:00 | 指标 | 内存占比98% |
| Redis02 | 18:16:00 | 指标 | 内存占比11% |
| Tomcat04 | 18:01:38 | 日志 | 出现 `GC (Allocation Failure)`，本次GC耗时约0.079秒 |
| Tomcat04 | 18:00:01.239 | 调用 | 一条调用耗时1,097毫秒，带有本次调用及父调用编号 |

例如第一类指标的原始字段是：`cmdb_id=Redis02`、`kpi_name=OSLinux-OSLinux_MEMORY_MEMORY_MEMUsedMemPerc`、`value=98.0`。程序依据编号分配节点，依据时间安排投递。调用记录在调用完成后才投递，避免提前知道它的最终耗时。

### ② 程序处理：原始记录变成工具观测

程序按节点保存所有已到达记录，再用现成工具整理：

| 数据类型 | 工具做什么 | 交给模型的材料是什么 |
|---|---|---|
| 指标 | 计算采样数量、范围、中位数、前后变化、极值时间，并记录告警 | 某个指标在指定范围内怎样变化 |
| 日志 | 按内容类别整理，保留次数、时间、明确错误和GC情况 | 某类运行事件或错误出现了多少次、何时出现 |
| 调用 | 统计次数、耗时、慢调用及逐分钟变化，用父子调用编号关联组件 | 哪些请求变慢，何时变慢，观察到了哪些组件连接 |

**一条“工具观测”是整理后的统计或事件说明，不等于一条原始记录。**重复告警合并记录，但出现、解除和再次出现的时间保留。

Redis02的20条内存采样被整理为：

> 共20个采样；范围11%～98%，中位数23%；前5分钟采样中位数23%，后5分钟为11%；18:10采样达到98%，18:16采样为11%。

程序确实找到了内存变化。这里的前后对照只描述本窗口内的观测，不保证前段正常，也不能仅凭这些统计认定内存泄漏。

### ③ 第一层筛选：为什么有27项，还有86项没进来

Redis02的2,158条指标记录，涉及**111种不同指标**。程序先计算每种指标的统计，再决定哪些进入首轮材料：曾触发告警、有明显变化、有无效值等质量问题，或者属于CPU/内存等预设对照指标的，优先进入。其余暂不送模型。

本题结果是：**111项指标统计中，25项进入首轮；86项没有进入。再加“没有日志”和“没有调用记录”两项说明，共27项。**86不是86条故障，也不是86条原始记录。它们的原始记录还在，可以重新查询，但4B首轮没有看到这些指标统计。

这层筛选是为了减少输入，依据是程序规则，**并没有证明未入选的86项都无用**。没有报警或不满足变化条件，不等于没有诊断价值。好在本题内存占比已经进入这25项，它是在下一层被漏掉的。

### ④ 第二层筛选：27项怎样选成12项

**12是程序设置的数量上限，不是模型能力测出来的必要上限，也不是已经找出的12条最重要证据。**当前代码按下面顺序选，重复项不再选，满12项就停止：

| 选择顺序 | 本题实际选入什么 | 新增数量 |
|---|---|---:|
| 每种模板先取遇到的第一项 | CPU使用率、无日志说明、无调用说明 | 3 |
| 每个名称类别再取第一项 | 文件系统容量、磁盘传输、缓存内存、网络连接数、Redis缓存未命中计数 | 5 |
| 补充尚未覆盖的变化形式 | CPU空闲相关指标，代表小幅变化 | 1 |
| 按原来的排列顺序补满 | CPU负载、系统时间、用户时间 | 3 |

这些指标的排列顺序会影响谁先被选到。**缓存内存先代表了“内存”这一类别，后面的“内存占比23%→98%→11%”就没有入选。缓存内存不能代替内存占比，它们描述的不是同一件事。**

按类别覆盖有减少重复的目的，但“同类只看一个、只看12项”并不可靠。**这道题已经确认：关键内存变化存在、工具也检出了，却没有送进4B首轮视野。原文还在，只表示以后有机会找回，不能说这层遗漏已经解决。**

### ⑤ 第三层筛选：4B为什么展开6项，最后选2项上报

**6和2都不是固定数量。**4B收到12项概要后，每项从三种处置中选择：展开查看、作为背景暂留、暂时不理解需要待查。本次选择6项展开、4项背景、2项待查。那两项待查是日志和调用数据缺失说明。

程序再给这6项准备填写表。对象、数值、时间、来源已填好；4B填写三种内容：

- **怎样解释：**从该表允许的选项中选，比如“中途高值”“前段较高”“普通运行事件”“证据不足”。
- **怎样处置：**上报、背景暂留、待查。
- **与哪项一起看：**可选其他观测编号，只表示有关联，不证明因果。

本次6项是CPU使用率、CPU负载、CPU系统时间、CPU用户时间、磁盘传输、缓存内存。4B选择CPU使用率和缓存内存上报，其余4项暂留。例如它对CPU使用率实际填了：

```text
程序已填：早段中位数0.881%，后段0.70975%，18:10采样达到8.0934%。
4B填写：解释＝早段较高、后段较低；处置＝上报；关联＝CPU负载。
程序组合：保留上述数值、时间和证据编号的报告语句。
```

这说明填空仍可能解释不全面：这次强调了前后差异，没有突出中间峰值。选项和填写是否合适，还需要检查。

**“2项上报”是4B主动选择的2项，不是中央只保存2项。**节点把全部27项工具材料及处理状态交给中央保存；这道题9B首轮实际读到了Redis02的2项上报和2项缺失说明，另外23项没有作为正文展示。程序虽有重点证据保留标记，但内存占比未进入首轮12项，这个标记没有让它自动出现在9B正文中。

各类填写模板如下；方括号内的数值和对象由程序填写，最后的解释与处置由4B选择：

| 模板 | 程序提供的填写句 | 4B选择什么 |
|---|---|---|
| 指标 | [组件]的[指标]早段[值]，在[时间]出现[值]，后段[值] | 稳定、波动、前段较高、后段较高、中途高值或证据不足；是否上报 |
| 日志 | [组件]在[起止时间]出现[日志类别]，共[次数]条 | 明确报错、普通运行事件或证据不足；是否上报 |
| 调用 | [组件]调用[次数]次，95%的调用不超过[耗时]，最长[耗时]，此前对照[耗时] | 相比对照变慢、存在个别长调用或证据不足；是否上报 |
| 连接 | 观测到[父节点]→[子节点]，对应调用统计为[次数与耗时] | 确认存在连接或证据不足；不能据此确认故障传播方向 |
| 告警 | [组件]的[信号]在[时间]触发规则，观测为[值] | 规则曾触发、仍需结合其他观测；是否上报 |
| 缺失 | [节点]在[范围]未收到[数据类型] | 保留未知或待补充，不能填成正常 |

不同指标的允许解释会根据材料变化，不是每张表都允许选择所有解释。**逐层变少不代表逐层更准确。前两层是程序筛选，后两次是4B选择；每层都可能漏掉对诊断有用的内容。**

### ⑥ 9B实际看了什么，580项怎样变成61项

**“一项工具观测”就是一份计算结果，例如Redis02某指标的半小时统计、Tomcat04某类GC日志的次数和时间，或者两个组件的一条连接统计。**不同观测可能来自同一件故障，甚至同一份数据的不同查询；这些数量不是故障数，也不是原始记录条数。

本题材料的实际来源是：

```text
18个节点的工具观测：532项
业务和实际调用连接的观测：43项
首次Tomcat04补查新增：5项
合计：532＋43＋5＝580项
```

**“默认展示”有明确的代码条件，不是9B先读完再挑：**

| 来源 | 什么情况下先准备展示 | 本题第一次补查后 |
|---|---|---:|
| 节点工具观测 | 4B选择上报，或目录选择待查/未处理，或填写失败需保留 | 31项 |
| 业务和实际调用连接 | 程序对这部分直接默认展示，没有让4B再挑 | 43项 |
| 节点补查返回 | 默认展示返回的工具结果，包括反证与缺失说明 | 5项 |
| 合计 | 31＋43＋5 | 79项 |

普通背景及未进入首轮目录的大部分材料不满足这些条件，先不放正文。这里不是按真实重要性打分；重点标记主要影响下一步超长时的保留顺序，并不能保证所有重点项都突破前面的筛选。

580项都保存在程序组织的中央材料里，并没有全部交给9B。第一次补查后的输入拼装实际经过：

| 步骤 | 程序做什么 | 结果 |
|---|---|---|
| 1 | 从580项中，先选节点上报、待查、补查和业务/连接等默认展示内容 | 先放入79项，另外501项正文暂不加载 |
| 2 | 加上题目、说明、节点总览等，计算整段输入长度 | 79项版本超过当前长度预算 |
| 3 | 按程序优先规则移出部分观测正文 | 移出18项，留下61项 |
| 4 | 把最终输入交给9B | 9B本轮看61项；580－61＝519项正文没看到 |

**61不是预先指定的数量，也不是9B选出的最重要61项。**当前程序把每轮输入、预留输出和修复余量合计限制为20,480 token；本轮预留2,000输出、700修复，实际输入17,488。每项文字长短不同，因此每轮能放多少项也不同。移出时倾向保留指定加载页、已引用证据、补查和重点标记，规则并不知道真实答案。

本轮61项里，43项是业务和调用连接观测，18项是组件及补查观测。**它并没有均衡读到18个节点的全部细节。**节点总览仍会提供其他概况，但总览不能代替没有加载的具体证据。

除了这些工具观测，输入里还有以下内容，它们也占用长度：

| 名称 | 实际是什么 |
|---|---|
| 题目 | 原始问题的时间范围、要求回答哪些字段、公开说明的故障数量；没有标准答案 |
| 节点总览 | 每个节点材料数量、处理范围及一段短说明，例如“Redis02本地保留27项观测”；不是27项的全部数值 |
| 系统背景 | 公开的组件和原因候选、系统与数据含义，帮助模型理解材料 |
| 操作说明 | 如何引用证据、如何提补查、工具实际能做什么；例如GC不等于OOM、缺失不等于正常 |
| 调查记录 | 此前提出的不同解释、未完成的问题、已经执行的查询与节点补充说明 |

超过长度后，程序倾向依次保留：明确要求加载的详情、先前引用的证据、补查类材料、重点标记。低优先级先被移出；同优先级仍受原顺序影响。这里也没有真正比较哪项对根因最关键。

**目录与正文是两样东西。**目录只有“编号、所属节点、主题、详情有几页”，例如：

```text
目录这一行：e320｜Redis02｜内存占比｜详情1页
                    ↓ 编号指向
工具材料e320：20个采样、范围11%～98%、中位数23%、18:10最高98%……
                    ↓ 来源记录可进一步追查
Redis02的对应原始指标采样
```

**编号指向580项中的某一项工具材料，不是只指向已展示的61项，也不直接等于某一行原始CSV。**本轮只加载61项，不会把它们重新编成1～61；所以本轮正文可以有e305、e578等编号。能看到e320这个目录名称，也不代表读到了e320里的数值。580项目录按每页24项排成25页：第1页是1～24项，第2页是25～48项，依此类推。目录页与这61项正文独立拼装，所以正文可能包含后面页的条目，不要求先读过它所在的目录页。

程序起初只给第1页目录。翻页要由9B明确提出，示例如下：

| 9B提出什么 | 程序下一轮给什么 |
|---|---|
| `read_pages:["directory:1"]` | 第2页目录，只是下一组名称和编号 |
| 读到某项编号后，提出 `read_pages:["e320:0"]` | e320这项已存工具观测的第1页详情 |
| 提出节点、时段、指标的工具请求 | 重新查询原始记录并计算，而不是翻已有材料 |

页码在程序中从0开始。翻页不会重新统计数据，也不会自动补出尚未保存的逐点序列。**本题9B没有提出翻页请求，各轮都停在第1页目录；它用了3次节点工具补查。**当前翻页和工具补查共用最多3次后续调查机会，没有自动遍历25页的保障。

本题实际执行的补查是：

| 次序 | 9B要求查什么 | 实际返回什么 |
|---|---|---|
| 1 | Tomcat04是否持续高CPU，并有OOM/内存泄漏迹象 | CPU范围26.24%～30.43%，内存85%～86%，以及GC等日志；4B将两项指标都标为“对所问判断证据不足” |
| 2 | 继续查Tomcat04的GC及错误日志 | GC等日志观测；4B将所填GC项解释为运行事件，没有确认OOM |
| 3 | 查Redis02内存使用率和日志 | 20点内存的统计及极值时间，包括98%；同时说明没有该范围日志，另一个请求指标没有记录 |

**这里的“证据不足”不是没有指标，而是4B没有确认9B所问的“持续高CPU、OOM或内存泄漏”。**但回复只有标签，没有说明具体理由，不能知道模型当时究竟如何考虑。从已提供的事实看，可以明确回复“CPU采样不支持持续高CPU”；而85%～86%的内存采样不能单独确认OOM。当前将整项问题笼统标成不足，没有分开写清“什么已回答、什么被反驳、什么仍未知”，也是接口缺陷。

补查结果追加保存。记录确认：第3次补查后，以及生成最终答案时，Redis02的98%和18:10极值确实进入了9B实际输入。

### ⑦ 程序没返回的变化过程，模型能不能补出来

工具用全部可用采样计算统计，但只输出了统计结果，没有逐点返回所有采样。这里不是中位数算错，而是**输出缺少回答时间变化问题需要的内容**。

例如“20个采样、中位数23%、最大98%、最高值首次在18:10”，没有表达本题实际存在的以下记录：

```text
18:09  23%
18:10  98%
18:12  98%
18:13  98%
18:15  98%
18:16  11%
```

这些记录表明多个采样处于高位，而不是只见过一次98%。没有采样的18:11、18:14仍未知，不能保证中间每秒持续98%。只给范围、中位数和一个极值时刻，无法充分回答“高值出现几次、何时开始、何时下降”。

**没有送给模型的事实，不能靠模型猜出来。**原始记录还在，就可以扩展固定工具：程序按请求读出这些采样，再计算高值次数、起止观测和采样缺口。4B解释结果，9B使用结果，不要求4B编代码或口算。

建议把工具返回分成三类，以下尚待实现：

- **工具能回答：**按问题返回统计、逐点序列、日志原文或具体调用记录。问完整序列，就不能只返回中位数。本题只有20点，可以全部返回。
- **有原文，但当前工具不会算：**明确说明尚不支持该统计，并提供范围明确、可分页的原始记录查看接口。简单文本含义可由4B理解；新的数值运算应补进现成工具。
- **原始数据也缺失：**写明缺什么，不能要求模型补造，不能把未知改成正常。

任意自然语言问题不能保证都能回答。协调者需要先知道工具实际能查什么；超出能力时返回“尚不能回答及原因”，保留该问题，而不是重复拿相同摘要冒充已完成。

### ⑧ 最终输出：模型选了谁，为什么算错

| 本题评分字段 | 标准答案 | 本次模型答案 | 判定 |
|---|---|---|---|
| 根因组件 | Redis02 | Tomcat04 | 错 |
| 根因原因 | high memory usage（内存占用高） | JVM Out of Memory (OOM) Heap（JVM堆内存溢出） | 错 |

**这道题两个要求字段均未答对，得分0。**模型还输出了18:01:38，但本题不对时间评分。

9B最终把Tomcat04的 `Allocation Failure` GC、较高内存和慢调用组合成了OOM判断。**这些观测并不能单独证明OOM；节点补查也没有确认OOM，但中央仍采纳了这个解释。**把本次9B的实际想法翻成普通话，就是：

> “Redis02也可能有内存问题，但我还不确定。我想继续看它的变化过程和日志。现在我更相信Tomcat04发生了OOM，所以最后回答Tomcat04。”

程序把“Redis02可能有问题、还不确定”标为 `unresolved`。这只是模型的暂定判断，不是标准答案，也不是程序已经排除了Redis02。**最终它选择了错误的Tomcat04，没选择正确的Redis02。**同时，Redis02本来就没有这类日志，不能因为找不到GC日志就削弱已有的内存证据。

## 4. 怎样改，才能让节点真正回答协调者的问题

以下区分尚待改进的部分，以及已接入、尚未做真实模型测试的新功能：

1. **完整概要分批看，不再每类只选一项。**让4B分批看完各指标和事件的简短概要；12可以是每页数量，不能变成整个节点只看12项。明确错误、首次重要变化必须优先展示。尚未展示的单独记为“未看”，不能归入“模型认为不重要”。
2. **按问题返回对应结果。**问一般变化就返回统计；问完整曲线就返回逐点时间和值；问高值持续情况，就由程序列出高值采样、首次/末次时间及采样缺口；问日志就返回相关原文与计数，问调用关系就返回对应的连接和耗时。工具不支持时明确返回不能回答，不能用同一份统计冒充完成。
3. **4B继续负责解释，不负责算数。**已接入详细填写表，明确表达已知、未知和下一步。原始逐点查询仍待扩展；本题只有20个内存采样，后续可以按需完整返回。
4. **9B要用返回结果核对自己的猜测。**GC不能直接证明OOM；没有日志是缺数据；有内存高值但原因未明，可以继续比较，不能要求所有节点都提供同一类证明。需要把明确反证、未完成问题和真正未读的材料告诉模型。

**本例已确认首轮漏见重要内存变化；后续又确认9B看见回补统计后仍答错。**这说明需要分别检查“材料有没有送到”和“模型有没有正确理解”，目前不能断言只修其中一项就能解决全部问题。

### 多给几个候选，能否检验9B是不是已经想到了正确答案

可以增加这个观察，但要把“候选列表里有正确答案”和“最终选对”分别报告。本题9B确实提出过Redis02/内存占用高，同时还认为Tomcat04/OOM更可信，最后选了后者。

建议保留最多3组按可信程度排序的候选，分别统计：首选是否正确，以及前三候选是否有一组完整正确。候选要成组保存时间、组件和原因；双故障题的一组候选应包含两件对应故障，不能把彼此竞争的两个猜测当成同时发生的两件故障。

**候选里包含Redis02是有价值的进展，但不能记成原评分下已答对。**现有评分器要求预测故障数与题目一致；单故障题直接提交三个故障会判零。已接入独立候选文件和候选命中评价，保留正常最终答案；尚未进行新版真实模型测试。

## 5. 本次修改：更完整的节点回复与多候选

**新功能已接入代码，使用独立开关；现有批量队列继续使用原来的填写和单一答案设置。**这样同一轮实验不会在中途混用两种方法。前面真实例子说明的是运行过的版本，不是下表的新回复。

4B现在可以在原有解释、处置和关联选择之外，再填写四栏。下面是依据Tomcat04真实统计给出的预期填写示例，**不是新增4B实测回复**：

| 新填写栏 | CPU项可以怎样回答 |
|---|---|
| 现象含义 | 本范围CPU采样占用不高，变化较小 |
| 能回答的部分 | 这些采样不支持持续高CPU |
| 还不能回答及原因 | 不能仅凭CPU判断调用变慢原因，也不能排除采样间隙的短时变化 |
| 需要补充什么 | 对齐同期调用和相关节点观测 |

程序仍附上真实数值、时间、单位和来源，不让模型重新计算。**原问题完整保留，不要求每个活的问题都正好对应一段固定程序。**工具只能回答一部分时，4B必须说清这部分与剩余缺口；不能只输出“工具不支持”就结束。

定向补查已限定节点、时间和工具，返回的材料现在全部分批交给4B填写，包括反证和缺失说明，不在返回后再用12项代表目录筛一次。解释与原问题一起传给9B，并标为待核实意见。下一步填写是一条建议，只有另行提出合法工具请求才会执行；不能执行的问题仍保留未知。新模式同时校正各节点“本轮实际加载多少”的计数，避免把保存数量误写成模型已读数量。

9B新增“首选＋最多两个备选”，每组都是完整的一套故障解释；双故障时每组各含两件故障。首选仍写入正常答案，备选独立保存和评分。候选重复或引用无效时会记录原因，不把错误备选混进首选。汇总分别显示首选正确率和前三候选完整命中率，附实际题数；没有候选文件的旧结果不混入候选命中率分母。

程序检查已覆盖填写字段、原问题保留、补查解释传给9B、候选排序与双故障配对、标签隔离、旧版兼容。它们验证接口连接，不证明真实模型已能正确填写或准确率已经提高。**初始12项目录与中央展示优先规则仍是前面描述的规则，完整曲线工具也尚未新增。**

新版入口已准备：[详细回复与多候选单题入口](../slurm/bank_case_detailed.sbatch)，默认只指定一道调试题，未提交作业；对应开关是 `--detailed-node-replies` 和 `--max-candidates 3`。目前仍使用本地4B和9B直接推理，没有PPO或经验库。
